\section{Conclusion}
We implemented Eclat from the original paper~\cite{zaki2000} as two variants that return
the same result. Both match SPMF's Eclat exactly at every database and threshold we
tested: across 330 outputs on 33 pairs, no itemset is missing, extra, duplicated, or
given the wrong support (Section~\ref{sec:exact}). In a single timing session on the
benchmark machine, the optimized variant is the fastest program at all 33 points. At the
lowest minsup of each database it runs 7.9 times (Accidents) to 33.3 times (Retail)
faster than the baseline (Section~\ref{sec:minsup}), and Section~\ref{sec:optimized}
breaks this gain down by optimization step. The baseline's time tracks the total length of
the tidsets it merges, at 2.0 to 6.9\,ns per element. At the lowest minsup of each
database, the optimized variant also uses 3.0\% to 34.5\% less peak memory than the
baseline (Section~\ref{sec:memory}). When the transaction length grows from 5 to 40 with
the output held fixed, the baseline's mining time grows 42-fold, while the optimized
variant's grows only 1.8-fold (Section~\ref{sec:width}).

Both applications use the same miner. On the 39\,516 invoices of Online Retail II, minsup
0.01 yields 1\,355 frequent itemsets, from which we generate association rules and rank
them by lift (Section~\ref{sec:basket}). On the 1\,593 Semeion images, a 24-word visual
codebook turns each image into a transaction, and the frequent itemsets describe stroke
combinations that recur across images (Section~\ref{sec:visual-patterns}).

These conclusions have limits. Every measurement ran on a single machine, the benchmark
machine, and programs are compared only within the same session. The \emph{process}
scope includes Julia or JVM start-up, which accounts for most of the time at high
thresholds, where the two Julia variants are close. Because we treat SPMF as a black box,
we do not explain the measured differences in terms of SPMF's internals. The basket data
comes from a single shop over two years, and the image patterns describe frequencies in
the same set that the codebook was learned on, so they say nothing yet about
classification accuracy.

The optimized variant's time profile points to two next steps (Section~\ref{sec:future}).
A flat integer store with an array-built vertical layout would cut the reading and layout
time that takes almost the whole run on Accidents, and writing the output in search order
would remove the sort that takes 35\% to 43\% of the profiler samples at the dense points.
Both are predictions with a plan for testing them, and neither has been implemented yet.
