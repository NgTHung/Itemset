\section{Implementation}
\label{sec:implementation}
We reimplemented Eclat from Zaki's original paper~\cite{zaki2000} in Julia, using only
the standard library and no frequent itemset mining (FIM) library. The package offers two
variants that return the same result: a baseline that stays close to the paper, and an
optimized variant. This section first explains how the algorithm works and why its output
is correct, then describes the interface, the optimizations we added, how we test both
variants, and how much each optimization gains over the baseline.

\subsection{Vertical layout and tidsets}
\label{sec:vertical}
Consider a database of $N$ transactions, numbered $1, 2, \dots, N$ in the order they are
read. This number is the transaction identifier (tid). Unlike Apriori's horizontal
layout, Eclat uses the vertical layout, in which each item $x$ is paired with its tidset
$t(x)$, the set of tids of the transactions that contain $x$. For an itemset $X$,
\begin{equation}
  t(X) = \{\, i \in \{1,\dots,N\} : X \subseteq T_i \,\}, \qquad
  \sigma(X) = |t(X)|,
  \label{eq:support}
\end{equation}
where $T_i$ is the $i$-th transaction and $\sigma(X)$ is the support of $X$, the number
of transactions that contain $X$. An itemset $X$ is frequent when
$\sigma(X) \ge \sigma_{\min}$, with $\sigma_{\min}$ the minimum support threshold
counted in transactions. When the same threshold is written as a fraction of $N$, we call
it $\mathit{minsup}$. An empty transaction still receives a tid and counts toward $N$,
even though it appears in no tidset.

The baseline stores each tidset as a sorted \texttt{Vector\{Int\}}, which we call a
tid-list. The function \texttt{to\_class} builds these lists in one pass over the
database, appending each tid as it reads the transaction, so every tid-list comes out
sorted and never has to be sorted again.

What makes the vertical layout attractive is that support follows from an intersection.
A transaction contains
$P \cup \{a, b\}$ if and only if it contains both $P \cup \{a\}$ and $P \cup \{b\}$, so
\begin{equation}
  t(P \cup \{a, b\}) = t(P \cup \{a\}) \cap t(P \cup \{b\}),
  \label{eq:intersect}
\end{equation}
where $P$ is an itemset and $a, b$ are two items not in $P$. The support of the new
itemset can therefore be computed from two tidsets that already exist, without scanning
the database again.

\subsection{Prefix-based equivalence classes and Bottom-Up search}
Zaki partitions the search space into prefix-based equivalence
classes~\cite{zaki2000}. The class with prefix $P$ holds the members
$(b, t(P \cup \{b\}))$, one for each item $b$ greater than every item of $P$ such that
$P \cup \{b\}$ is frequent. Itemsets in the same class share everything except their
last item, which is why identity~\eqref{eq:intersect} applies only to two members of the
same class.

The function \texttt{bottom\_up!} implements the paper's Bottom-Up procedure. For each
member $a$ of the class with prefix $P$, it records $P \cup \{a\}$ and its support,
intersects $t(P \cup \{a\})$ with the tidset of every member $b$ after $a$, keeps the
frequent results as the child class with prefix $P \cup \{a\}$, and searches that child
class before moving to the next member. The search starts from the root class, whose
prefix is empty and whose members are the frequent items. The paper allows either a
depth-first search (DFS) or a breadth-first search over the lattice of classes and
presents its results breadth-first. We chose DFS because it keeps only one class per level
of the current path in memory. The paper also finds the frequent 2-itemsets up front by
counting them in a triangular array over the horizontal database. The baseline skips that
step and starts intersecting from single items, so a single procedure handles every
level; the optimized variant brings the counting step back
(Section~\ref{sec:optimized}). Table~\ref{tab:mapping} shows where each part of the paper
lives in the source code.

\subsection{Correctness}
\label{sec:correctness}
Every class that \texttt{bottom\_up!} receives satisfies four invariants: (i) each
tid-list is increasing and has no duplicates; (ii) the members are sorted by item and
every member item is greater than every item of the prefix; (iii) every member is
frequent; (iv) the tid-list of member $b$ equals $t(P \cup \{b\})$. The root class
satisfies all four by construction. A child class inherits (i) and (ii) because it is
built from the members that follow $a$; the support check made before each member is
added guarantees (iii), and identity~\eqref{eq:intersect} guarantees (iv).

These invariants make the output correct in three ways. First, every recorded support is
exact, which follows from (iv) and~\eqref{eq:support}. Second, no itemset is recorded
twice. By (ii), every key $(x_1, \dots, x_k)$ is strictly increasing, it is recorded only
when the class with prefix $(x_1, \dots, x_{k-1})$ reaches $x_k$, and each class is built
only once. Third, the result is complete because support is
anti-monotone~\cite{agrawal1994}: if $X \subseteq Y$, every transaction that contains $Y$
also contains $X$, so by~\eqref{eq:support} $t(Y) \subseteq t(X)$ and
$\sigma(X) \ge \sigma(Y)$. Pruning an infrequent itemset therefore never loses a frequent
superset. An induction on length shows that the class with prefix
$(x_1, \dots, x_{j-1})$ contains every item $y > x_{j-1}$ for which
$(x_1, \dots, x_{j-1}, y)$ is frequent, and therefore every frequent itemset is recorded.
Appendix~\ref{app:baseline} gives the full proofs.

\subsection{Complexity}
Let $L$ be the total number of items over all transactions, $m$ the number of distinct
items, and $C$ the number of intersections. Building the vertical layout takes $O(L)$
expected time to fill the dictionary, $O(m \log m)$ to sort the items, and $O(L)$ memory.
Intersecting two tid-lists costs $O(|t(P \cup \{a\})| + |t(P \cup \{b\})|)$, which is
never more than $O(N)$, and a class with $k$ members performs $k(k-1)/2$ intersections.
The total time is therefore
\begin{equation}
  O(L + m \log m + C \cdot N),
  \label{eq:cost}
\end{equation}
where $C$ is the total number of intersections over all classes visited. Because the
search is depth-first, memory only has to hold the classes on the current path: one class
per level, each with at most $m$ members of at most $N$ tids. The output, on the other
hand, can grow exponentially, since a frequent $k$-itemset has $2^k - 1$ non-empty
subsets and all of them are frequent.

\subsection{Interface, SPMF format, and command line}
The two applications and the experiments use only four public functions:
\texttt{read\_transactions} reads an SPMF file, which has one transaction per line with
items separated by spaces; \texttt{support\_threshold} converts a threshold to a
transaction count; \texttt{mine} returns a \texttt{SupportMap} dictionary from itemset to
support; and \texttt{write\_itemsets} writes one itemset per line in the form
\texttt{1 2 \#SUP: 2}. A real threshold in $(0, 1]$ is read as the fraction
$\mathit{minsup}$ and rounded up to $\sigma_{\min} = \lceil \mathit{minsup} \cdot N \rceil$
transactions, while an integer threshold is taken as $\sigma_{\min}$ directly. The
\texttt{variant} argument selects \texttt{:baseline} or \texttt{:optimized}, so either
variant can be run on its own and the two can be compared on the same input.

The command-line program \texttt{demo.jl} takes an input path, an optional
\texttt{--output} (stdout when omitted), exactly one of the two thresholds \texttt{--minsup} (a fraction) or
\texttt{--min-count} (a transaction count), and \texttt{--variant}, for example
\texttt{julia --project=. demo.jl --minsup 0.5 --output out.txt data/toy/baskets.txt}.
On invalid input the program exits with code 1 and a message that names the offending
line. Because the writer validates the whole result before it opens the file, a failed
run leaves any existing output file untouched. Itemsets are written in lexicographic order
of their item codes, which makes the output files of the two variants identical byte for
byte.

\subsection{Optimized variant}
\label{sec:optimized}
The optimized variant keeps the Bottom-Up procedure and changes three things: how
tidsets are stored, which intersections are skipped, and how the result is written. None
of these changes alters the output, as Appendices~\ref{app:perfect} and~\ref{app:skips}
prove. Start-up, reading, and writing live in code that both variants share, so the
baseline benefits from the changes made there as well.

\subsubsection{Bitset tidsets and search order}
At the lowest threshold of each database, the baseline's mining call allocates 3.3 to
5.7 GiB, mostly for the new tid-list that each intersection creates. The optimized variant
stores each tidset as a bitset instead: a string of $W = \lceil N/64 \rceil$ 64-bit words
in which bit $i$ stands for transaction $i$. Intersecting two bitsets is a word-by-word
AND, and the same loop counts the set bits with \texttt{count\_ones} to get the support.
The result is written into a bitset taken from a reusable pool, and if the intersection
turns out infrequent, the bitset goes straight back to the pool, so a failed intersection
allocates no memory. Every intersection reads $2W$ words regardless of the support, with
$W = 50$ on Chess and $5\,316$ on Accidents.

The optimized variant also visits items in increasing order of support. The rare item
that comes first is intersected with the most items, but most of those intersections
fail; the frequent item that comes last has few members after it, so its child classes
stay small. The proof in Section~\ref{sec:correctness} only needs some total order on the
items, so it holds for this order as well.

\subsubsection{Perfect-extension pruning and single allocation of the result}
An item $b$ is a perfect extension~\cite{borgelt2012} of an itemset $X$ when
$t(X \cup \{b\}) = t(X)$, that is, when every transaction that contains $X$ also contains
$b$. Since $t(X \cup \{b\}) \subseteq t(X)$, the condition is equivalent to the two
supports being equal, so comparing two counts is enough to decide it. If $E$ is the set of
perfect extensions of $X$, every itemset $X \cup Y$ in the subtree of $X$ has the same
support as $X \cup Y \cup S$ for any subset $S$ of $E$. The optimized variant therefore
drops $b$ from the child class and never intersects $b$'s tidset again, and each node of
the search tree stands for $2^{|E|}$ itemsets with the same support. On Mushroom 0.05,
this shrinks the search tree to 33\,819 nodes for 3\,755\,511 itemsets.

During the search, the program records only the nodes, in preorder, with the depth of
each node, the item it adds, the perfect extensions it found, and its support. Afterwards,
\texttt{expand\_nodes} computes the final size of the result from the nodes (with an
overflow check), allocates the three result arrays exactly once, and writes out the
subsets $S$ in Gray-code order, so that two consecutive itemsets differ by one item.
Growing the arrays one itemset at a time would instead copy the whole array at every
doubling of capacity. On Mushroom 0.05, in an already warm process, that approach
allocated 1\,068 MiB to build a 306 MiB result and took 0.40 s; with a single allocation
the same call allocates 310 MiB and takes 0.17 s.

\subsubsection{Sparse data: pair counting, tid lists, and block bounds}
On sparse data, a bitset intersection still reads all $W$ words even when the tidsets are
short ($W = 1\,378$ on Retail and $1\,563$ on T10I4D100K), and most intersections fail
anyway. On Retail 0.001, 99.9\% of the 2\,239\,786 intersections in the root class miss
the threshold. On T10I4D100K 0.00025, most intersections happen at depth 2, where
2\,256\,822 of them (99.1\% failing) work on tidsets of only about 100 tids. The following
three techniques target these two patterns.

\emph{Pair counting at the root.} The function \texttt{count\_pairs} counts the support
of every pair of frequent items in a triangular array of $m_f(m_f-1)/2$ cells during one
pass over the horizontal database, as in Section 5.1 of the paper~\cite{zaki2000}, where
$m_f$ is the number of frequent items. The root class then intersects only the pairs that
reach the threshold. Since the prefix at the root is empty, the count of a pair $(a, b)$
is exactly $|t(\{a, b\})|$, so no frequent intersection is skipped. The counting runs only
when its estimated cost is below one tenth of the cost of the root intersections, that
is, when
$10 \sum_i |T_i|(|T_i| - 1)/2 < W m_f(m_f-1)/2$. Retail and T10I4D100K meet this
condition when many items are frequent, but not at Retail 0.01, where few items are
frequent and the root intersects as before (Table~\ref{tab:stage-profile}). Chess,
Mushroom, and Accidents, with their long transactions and few frequent items, never meet
it.

\emph{Per-class tid lists.} A child class with $k$ members switches from bitsets to
increasing tid lists when
\begin{equation}
  kW + c\,(k - 1) \sum_{i=1}^{k} \sigma_i < W\,\frac{k(k-1)}{2},
  \label{eq:lists}
\end{equation}
where the right-hand side is the number of words the class's bitset intersections would
read, $kW$ is the cost of the conversion, $\sigma_i$ is the support of the $i$-th
member, and $c = 8$ is the cost of one merge step in words, chosen from a sweep of $c$
from 2 to 16 on the grading machine. Rule~\eqref{eq:lists} looks only at tidset lengths
and $N$, never at which database is being mined. Each step of the merge advances through the two
lists without a branch on the compared tids, and a bound check before each step stops the
merge once the common tids found so far plus the rest of the shorter list cannot reach
$\sigma_{\min}$.

\emph{Block bounds.} Even with tid lists, 98.7\% of the 2\,076\,972 merges on
T10I4D100K 0.00025 still fail, on pairs of lists that hold 126 tids between them on
average. Before searching a class of tid lists, the program therefore splits the tid range
into at most $K = 256$ blocks, each a power of two wide, and counts how many tids of each
member fall in each block. For two members $X$ and $Y$ of the class,
\begin{equation}
  \sigma(X \cup Y) \le \sum_{j=1}^{K} \min(c_{X,j}, c_{Y,j}),
  \label{eq:bound}
\end{equation}
where $c_{X,j}$ and $c_{Y,j}$ are the numbers of tids of $X$ and $Y$ in block $j$,
because a common tid lies in exactly one block and is counted once for each member. When
this bound is below $\sigma_{\min}$, the program skips the merge without reading a single
tid. Bound~\eqref{eq:bound} never rejects a frequent intersection, so the output stays the
same. We chose $K = 256$ after sweeping 64 to 512 blocks.

\subsubsection{Start-up, reading, and writing}
The changes in this subsection are in the code that both variants share. At high
thresholds, little of the runtime is spent in the algorithm itself. One \texttt{demo.jl}
process of the baseline on Chess 0.9 takes 2.36 s, of which Julia start-up accounts for
only 0.17 s; the rest is just-in-time (JIT) compilation. To avoid it, we run the public
functions and the command-line handling on a small database while Julia builds the
package image, so their machine code is stored with the package. The command-line
handling lives in the package (\texttt{src/cli.jl}) rather than in the script, because
script code is not stored in the package image and would be recompiled, at a cost of
108.6 ms, on every run. A test runs \texttt{demo.jl} in a fresh process with
\texttt{--trace-compile} and fails if any method needs compiling.

At low thresholds on dense data, writing the result takes most of the time. Sampling
Mushroom 0.05 with \texttt{Profile} showed the comparison sort of the output at 64\% of
the time, formatting and writing the file at 25\%, and mining at only 11\%. The sort is
needed because the optimized variant visits items by support and must put the result
back into lexicographic order, so we replaced it with a radix sort on a 128-bit key that
holds the first items of the itemset and its index. The writer now looks up the digits of
every number below $2^{20}$ in a table and writes them with a single 8-byte store. The
reader parses each line into a reused vector and copies it once at its final length; as
a result, reading Accidents (34 MB) in a warm process takes 0.29 s instead of 0.57 s and
allocates 151 MiB instead of 354 MiB.

\subsubsection{Julia features}
The type \texttt{ClassMember\{T\}} takes a parameter \texttt{T}, which is \texttt{UInt64}
for bitsets and \texttt{Int} for tid lists. The search function \texttt{eclat\_search!}
is written only once; multiple dispatch, which chooses a method from the types of all
arguments, picks the right intersection, conversion rule, and intersection filter for
each \texttt{T}. Julia compiles a specialized copy of the search for each tidset form, so
the inner loop runs without type checks. We use \texttt{Vector\{UInt64\}} rather than
\texttt{BitVector} because the intersection loop writes into reused memory and counts
bits in the same pass.

The key type of \texttt{SupportMap}, \texttt{Tuple\{Vararg\{Int\}\}}, has no fixed length,
and building millions of such keys costs more than the mining itself. In an early test on
Mushroom 0.05, inserting 3.76 million itemsets into the dictionary took 12.4 s, while
counting their supports took only 0.63 s. Both variants therefore write their result into
three flat \texttt{Vector\{Int\}} arrays holding the items, the start position of each
itemset, and the supports. The file writer reads these arrays directly, and \texttt{mine}
builds a \texttt{SupportMap} only at the interface boundary, for the applications. Every
tuning constant is \texttt{const}, and every container on a hot path has a concrete
element type. \texttt{@inbounds} appears only in the tid-list merge and the number writer,
each time with a comment that proves the indices valid. On the bitset intersection loop,
\texttt{@inbounds @simd} changed mining time by $-8\%$ to $+11\%$ over five measurement
points, which is within noise, so we left it out.

\subsection{Automated tests}
\label{sec:tests}
The command \texttt{julia --project=. test/runtests.jl} runs 1\,500 checks, and all of
them pass on Julia 1.13.2. Each mining test compares the whole \texttt{SupportMap} and
also checks the number of itemsets recorded, since a dictionary would silently hide an
itemset recorded twice. Both variants go through the following groups of tests.

\begin{itemize}
\item Hand-derived results: eight small databases, including an empty database, a
database with no frequent itemset, duplicate transactions, thresholds just above and
just below an itemset's support, and an image database with empty transactions.
\item Comparison with SPMF's Eclat~\cite{spmf2016}: eight runs on seven small databases
and one run on T25I10D10K (9\,976 transactions, 929 items), where SPMF reports 14\,782
itemsets of 1 to 13 items at $\mathit{minsup} = 0.008$. Both variants match 100\% on all
nine runs, with no missing, extra, or wrong-support itemset.
\item Comparison with a brute-force counter that enumerates every subset, on 10 random
databases generated with seed 42 for each variant. The optimized variant is also tested
on eight databases with 0, 1, 63, 64, 65, 127, 128, and 129 transactions, sizes that
straddle the boundary of a 64-bit bitset word. Half of them contain groups of items that
always occur together, so that perfect extensions appear. Each database is mined under 18
configurations that turn the techniques of Section~\ref{sec:optimized} on and off.
\item Type stability: \texttt{Test.@inferred} on \texttt{mine}, \texttt{mine\_packed},
and the search functions of both variants.
\item Reading, writing, and the command line: the byte-level reader is checked against a
line-based parser on edge-case inputs (\texttt{Int} overflow, unexpected characters,
blank lines, Windows line endings) and on every small database. The writer's output is
compared byte for byte with a reference formatter, and the tests also cover argument
errors and process exit codes.
\end{itemize}

The brute-force counter is too slow for anything but tests. For the benchmarks, every
measurement campaign instead compares each output file with an independent run of SPMF's
Eclat once timing has finished. In the runtime campaign of Section~\ref{sec:minsup}, all
660 output files on the five benchmark databases, 165 from each of the four programs,
match 100\%.

\subsection{Measuring the improvement}
\label{sec:measure}
Every number in this subsection is the median time of five cold \texttt{demo.jl}
processes, where each run is a fresh process that covers Julia start-up, reading, mining,
and writing the file. The campaigns ran on the grading machine described in
Section~\ref{sec:protocol}, over a grid of 33 thresholds on the five databases Chess,
Mushroom, Retail, T10I4D100K, and Accidents, plus a few stress thresholds below the grid
that only probe the limits. Besides SPMF's Eclat, we compare with
PrePost+~\cite{deng2015} from the
\href{https://github.com/NgTHung/Itemset/blob/main/tools/spmf/release.toml}{pinned SPMF release},
because it is faster than SPMF's Eclat on dense data. The ratio
$R = T_\text{opt} / T_\text{PrePost+}$ is the median time of the optimized variant
divided by the median time of PrePost+ at the same threshold.

Each technique was measured in its own session, with the versions before and after the
change alternating on every repeat so that machine drift affects both equally. The one
exception is Step~\ref{step:precompile-package}, the package precompilation, which was
measured as two consecutive campaigns. Table~\ref{tab:steps} gives, for each step, the
range of after-over-before time ratios over the 33 thresholds and the matching
peak-memory ratios. Peak memory here is the peak resident set size (RSS), the largest
amount of physical memory the process holds, as reported by the operating system.

Step~\ref{step:bitset} has by far the largest effect: it brings the time down to between
10\% and 97\% of the baseline (median 37\%) and lowers peak memory at every threshold.
Step~\ref{step:pair-count} matters only on sparse data, where it cuts the time of
Retail 0.001 by 76\%. On its own, Step~\ref{step:perfect-extension} shortens process time
by at most 6.9\%, because at that point sorting and writing hundreds of thousands of
itemsets still takes most of the time. We kept it anyway, since it does not raise memory
and Step~\ref{step:single-allocation} builds on it. No step slows any threshold by more
than 4.4\%.

Table~\ref{tab:steps} documents how the optimized variant was built one step at a time; it
does not compare the two submitted variants. Steps~\ref{step:precompile-package},
\ref{step:precompile-cli}, and~\ref{step:byte-io} changed shared code, so the submitted
baseline benefits from them too. The speedups this paper reports come from
Section~\ref{sec:minsup}, which compares the two submitted variants at one revision in a
single session.

We also tried three techniques that did not survive measurement. Diffsets~\cite{zaki2003}
store the tids a member lacks relative to its prefix. In a sweep of the switching ratio,
no setting beat bitsets: Accidents 0.2 slowed by up to 10\% and T10I4D100K 0.00025 by up
to 71\%. The reason is that perfect-extension pruning already removes every member with
an empty diffset, which is exactly where diffsets help most; even choosing the best
representation for each class would have cut the words read by at most 0.3\%. Printing
itemsets directly from the sort key was 5\% to 7\% slower, and \texttt{@inbounds @simd} on

The optimized variant still has three measured limits. At the stress threshold
Mushroom 0.05 it has to write 3\,755\,511 lines and remains slower than PrePost+ (1.45 s
against 1.38 s). Every process spends about 0.19 s on Julia start-up and package loading,
which only ahead-of-time compilation into an executable could remove. Finally, pair
counting raises peak memory by 20\% at the stress threshold Retail 0.00025, where the
triangular array for 5\,918 frequent items takes 67 MiB.
